# 版本迁移指南（migration.md）

novel-cards v1.0 提供**版本迁移文档**能力：定义版本策略、五条兼容原则、升级判定四档、
回滚四步与废弃三档策略，使使用方工程在跨版本升级时有明确的改动点说明与操作路径。

本仓库内 `MIGRATION.md` 只以模板骨架形式存在（由 `install.sh --project` 生成占位），
真实内容由使用方工程随版本迭代填充。本文档是 skill 侧的规范契约，`install.sh --project`
生成的 `MIGRATION.md` 兜底版是其最小投影。

## 1. 版本策略声明

版本号格式：**主版本.次版本-标记**（如 `1.0` / `0.9-beta`）。

| 档位 | 标记 | 策略 |
|---|---|---|
| **0.x** | 实验版 | schema 可能变动，不保证向前兼容；建议升级前手动备份 `history/` + `cards/` |
| **1.x** | 稳定正式版 | schema 变动优先做兼容层，重大改动才强制迁移；系统内置自动迁移转换 |

当前基线版本 MUST 在使用方工程 `MIGRATION.md` 顶部明确标注。

### WHEN/THEN 判定示例

| 场景 | WHEN | THEN |
|---|---|---|
| 实验版升级提示 | 使用方工程当前为 0.x 版本，准备升级到下一 0.x | MIGRATION.md 提示「实验标记版本，建议升级前手动备份 history + cards」 |
| 稳定版升级 | 使用方工程从 1.0 升级到 1.1 | 系统内置自动迁移转换，无需手动操作（除非触发破坏性变更） |

## 2. 五条兼容原则

后续所有版本 MUST 遵守以下五条兼容原则：

| # | 原则 | 说明 |
|---|---|---|
| 1 | **字段新增不改旧卡** | 旧卡片无需改动，缺失字段自动取默认值（向后兼容） |
| 2 | **改名删除需迁移脚本** | 字段改名/删除属破坏性变更，必须写迁移脚本或手动迁移步骤并在 MIGRATION.md 置顶 |
| 3 | **skill 别名永久保留** | skill 中英别名一旦发布尽量永久保留，不随意废除 |
| 4 | **规则 ID 永久不变** | 规则 ID（SPACE_001 / BEAT_001 / PERSON_001 等）一旦定义永久不变，只修改规则逻辑 |
| 5 | **profile_override 机制保留** | 全局/单卡片剖面切换机制作为底层基础能力保留不砍 |

### WHEN/THEN 判定示例

| 场景 | WHEN | THEN |
|---|---|---|
| 新增字段向后兼容 | 新版本为 sensory_cue 卡新增 `maskable` 字段 | 存量无该字段的 cue 卡按默认值（false）处理，无需迁移，nc-校阅 行为不变 |
| 字段改名触发迁移 | 新版本将 `pre_visible_delay` 改名为 `signal_lead_time` | MIGRATION.md 置顶破坏性变更清单，提供方案 A（nc-migrate 自动遍历替换）或方案 B（手动批量替换表格），升级后执行 nc-校阅 --full 验证 |
| 规则 ID 不变 | 新版本修改 SPACE_001 的校验逻辑但保留 rule_id | 存量 rules.json 无需改动，仅规则行为变化 |

## 3. 升级判定四档

| 档位 | 判定条件 | 操作 |
|---|---|---|
| ✅ **非破坏性** | 仅新增卡片类型 / 规则 / skill | 直接继续用旧卡，无需迁移 |
| ⚠️ **破坏性** | 字段重命名 / 结构重构 / 删除必填字段 | 提供迁移步骤（方案 A 自动 / 方案 B 手动） |
| 🧪 **实验版** | 0.x → 下一 0.x | 建议升级前手动备份 `history/` + `cards/` |
| 🚀 **稳定版** | 1.0+ 重大升级 | 系统内置自动迁移转换 |

### WHEN/THEN 判定示例

| 场景 | WHEN | THEN |
|---|---|---|
| 非破坏性升级 | 新版本仅新增 FACTION_001 规则与势力卡新可选字段 | 判定为 ✅ 档，使用方工程无需任何手动操作 |
| 破坏性升级 | 新版本将 `tension_base` 改名为 `tension_level` 并删除 `is_strategic_climax` | 判定为 ⚠️ 档，MIGRATION.md 置顶迁移清单，提供自动/手动两种方案 |

## 4. 回滚四步

升级失败时按以下四步回滚到升级前状态：

1. **找快照**：进入 `history/` 找升级前自动生成的快照目录（`snapshot_<YYYYMMDD_HHMMSS>_{cards,meta}`）
2. **覆盖恢复**：将快照内 `cards` + `meta` 文件覆盖回项目根
3. **恢复配置**：恢复 `config/project.yaml` 为升级前版本
4. **验证引用**：执行 `nc-检索` 抽查资产 ID 引用是否正常

### WHEN/THEN 判定示例

| 场景 | WHEN | THEN |
|---|---|---|
| 升级失败回滚 | 升级后 nc-校阅 --full 报大量悬空 ID | 按四步回滚到升级前快照，恢复后 nc-检索 抽查确认引用正常 |
| 部分升级回滚 | 升级后部分卡片字段解析失败 | 回滚整个快照（不做部分恢复），避免半升级状态 |

## 5. 废弃策略三档

| 档位 | 处理方式 |
|---|---|
| **废弃 skill** | 保留别名，调用时输出「该 skill 已废弃，推荐使用 xx」提示，仍执行原逻辑（过渡期内） |
| **废弃标签/旧字段** | 校阅时输出 L3_INSPIRATION 提示，不抛 L1/L2 错误给过渡期 |
| **超过两个大版本的废弃字段** | 在下一个版本彻底移除 |

### WHEN/THEN 判定示例

| 场景 | WHEN | THEN |
|---|---|---|
| 废弃 skill 软提示 | 作者调用已废弃的旧 skill 别名 | 系统输出废弃提示并推荐替代 skill，仍执行原逻辑（过渡期内） |
| 废弃字段 L3 提示 | 存量卡含已废弃字段 `old_field_name` | nc-校阅 输出 💡L3「该字段已在 v1.2 废弃，建议迁移至 new_field_name」，不抛 L1/L2 |

## 6. 与 build.sh 历史快照的协同

`build.sh` / `build.cmd` 每次执行 SHALL 向 `history/` 写入一份完整快照（卡片全量 +
元文件），与 `CHANGELOG.md` 形成双重回溯机制。快照目录命名 `snapshot_<YYYYMMDD_HHMMSS>`。

- **回滚依据**：升级失败时从 `history/` 找到升级前快照目录，将 `cards` + `meta` 覆盖回项目根即可恢复
- **MUST NOT 自动清理旧快照**：由作者自行定期清理
- **多次 build 累积**：连续执行 N 次 build.sh → `history/` 下累积 N 个不同时间戳的快照目录，互不覆盖

详见 `references/build-contract.md`（build 脚本职责边界契约）。

## 7. 规范可见性

- **SKILL.md body**：硬规则速览区含版本迁移摘要（指向本文档）
- **references/migration.md**：本文档（完整五原则 + 四档 + 四步 + 三档）
- **install.sh --project 生成的 MIGRATION.md**：最小占位版（当前基线版本 + 待填充区）
- **使用方工程 MIGRATION.md**：真实内容，每次版本升级追加改动点清单 / 迁移步骤 / 验证命令
